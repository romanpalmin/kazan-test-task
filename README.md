# kazan-test-task

Магазин цифровых товаров для геймеров — бэкенд с упором на однократную
выдачу под гонками. Витрина (Этап 1) ещё не сверстана — этот README
пока описывает то, что реально работает: API заказов, вебхук оплаты и
выдача ключа.

## Запуск

```bash
npm install
npm run seed   # каталог + пул ключей в data/app.db (не в git)
npm start      # http://localhost:3000
```

## Как проверить однократную выдачу под гонками

```bash
npm run test:race
```

Скрипт сам поднимает сервер на отдельном порту (3999, не мешает `npm
start`), сбрасывает БД в чистое состояние и прогоняет три сценария —
ничего поднимать вручную не нужно:

1. **50 параллельных вебхуков, один и тот же `event_id`** (двойной
   клик / ретраи платёжки) — ровно один применяется, остальные видят
   `duplicate:true`, ключ расходуется один.
2. **50 параллельных вебхуков, 50 разных `event_id` на один заказ** —
   ключ всё равно расходуется ровно один: здесь защищает не дедуп
   событий, а атомарный переход статуса заказа (`created → paid`).
3. **Вебхук приходит раньше, чем создан заказ** — платёж не теряется,
   применяется автоматически, как только заказ появляется.

### Почему сценарий 3 проверяется иначе, чем 1 и 2

Сценарии 1 и 2 бьют по-настоящему в HTTP, параллельными запросами к
поднятому серверу. Сценарий 3 вызывает напрямую `paymentService.js` —
тот же код, который вызывает `POST /webhook/payment` — а не через HTTP.

Причина не в удобстве, а в архитектуре: `order_id` генерирует сам
сервер (случайный UUID) в момент создания заказа. Снаружи невозможно
заранее знать id заказа, которого ещё не существует, чтобы честно
отправить на него вебхук через HTTP и потом создать именно этот заказ.
Единственный способ сделать это через чистый HTTP — разрешить клиенту
передавать свой `id` в `POST /orders`, то есть менять публичный
контракт ради одного тестового сценария. Решили не делать эту правку
ради скорости.

Вместо этого вызывается напрямую тот же код, который вызывает
HTTP-роут (`applyPayment`, `parkPayment`, `drainPendingPayment` —
всё с реальной БД, реальными транзакциями, ничего не замокано).
HTTP-обёртка (распарсить тело → вызвать сервис → сформировать ответ)
не добавляет никаких гарантий к этой конкретной логике — сокращена
только точка входа, а не сама проверяемая механика.

## Как обеспечена однократная выдача — коротко

Три независимых атомарных «шлюза», без блокировок на уровне приложения:

- **Вебхук:** `INSERT` в `processed_webhook_events` c `event_id` как
  первичным ключом — сама вставка гасит повторы.
- **Статус заказа:** `UPDATE orders SET status='paid' WHERE
  status='created'` — атомарный переход, защищает от гонки даже если
  `event_id` у запросов разные.
- **Ключ:** `UPDATE keys_pool SET order_id=? WHERE order_id IS NULL` —
  атомарное занятие одного свободного ключа.
- **Поставщик:** `issuer_ledger` проверяется первым шагом любого
  обращения к поставщику — повтор после таймаута возвращает тот же
  код, а не выдаёт новый (поставщик мог успеть выдать код, ответ мог
  потеряться).

## Этап 3 — восстановление после сбоя (админка)

`/admin.html` — отдельная страница, не связана с витриной ссылками
(дизайн намеренно не проработан, заданием он не требуется). Все запросы
— с заголовком `X-Admin-Token` (по умолчанию `kazan-admin-dev`, меняется
переменной окружения `ADMIN_TOKEN`).

- Список заказов «оплачен, но не выдан» (`out_of_stock`/`delivery_failed`).
- Пополнение пула ключей по SKU.
- Кнопка «Повторить» — ручная повторная выдача.

Повторная выдача идемпотентна тем же способом, что и автодоставка после
оплаты (§ ниже) — до пополнения пула повтор безопасно оставляет заказ в
прежнем статусе, параллельные клики по «Повторить» на одном заказе дают
ровно одну выдачу. Как истощить пул для проверки — см.
`docs/backend-architecture.md`, §12.
